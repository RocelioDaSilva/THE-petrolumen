# PetroLúmen Workspace Document Review

**Review date:** 1 November 2026
**Workspace:** `C:\Users\rocel\THE-petrolumen`
**Purpose:** Assess the workspace's document organization, currentness, duplication, discoverability, and improvement opportunities.

## Executive summary

The workspace has useful engineering, onboarding, audit, competition, and project-planning material, but it does not yet have one reliable documentation source of truth. Current root-project guidance is mixed with documentation for older architectures, copied repositories, generated files, public web assets, competition records, and a large external reference library.

At inventory time, the scan identified **2,664 files (about 718 MB)** outside excluded Git metadata, dependency, cache, and build-output directories. It found **327 document-format files**: 179 Markdown, 51 plain text, 58 PDF, 23 HTML, 8 TeX, 3 PowerPoint, 2 Word, 2 reStructuredText, and 1 EPUB file. The 58 PDFs accounted for about 464 MB.

Most important findings:

1. **Conflicting setup guidance (corrected):** the prior [`CONTRIBUTING.md`](../CONTRIBUTING.md) described Next.js/pnpm in a `petrolumen/` app directory, while root manifests identify Vite/npm. The contributor guide now identifies the root app and documents its npm and backend workflows.
2. **Historical audits are presented beside current guidance without clear status.** Several reports date from July or October 2024 and describe a different backend/frontend architecture from the current root manifests and [`backend/README.md`](../backend/README.md). [`ENVIRONMENT_STATE.md`](../docs/ENVIRONMENT_STATE.md) itself says it was last verified in 2024.
3. **Duplication and unclear authority:** exact-content comparison found 42 duplicate groups across document files, with 73 redundant copies. A number of audits appear in both `docs/`, competition archives, `public/assets/aistudio/`, and copied project trees.
4. **Maintenance gaps:** [`docs/plans/updates.md`](../docs/plans/updates.md) contains an unexpanded shell date expression; it remains to be corrected or archived. The security contact placeholder has been replaced with GitHub private vulnerability reporting in [`SECURITY.md`](../SECURITY.md).
5. **Mixed-purpose storage:** reference books, registration forms, business-plan submissions, presentations, a course list, and a meeting transcript sit alongside software documentation. Some registration material may contain personal information; reference-library files need provenance and redistribution-rights review.

The cleanup has designated the root Vite/React application and `backend/` as canonical, labeled the documentation archive, and moved reference and private records out of the repository. Remaining priorities are history cleanup, reconciliation of stale audit evidence, and careful deduplication of local copies.

## Scope and method

- Inventoried the workspace recursively while excluding `.git`, `node_modules`, Python virtual environments, `__pycache__`, and common build output (`dist`, `build`, `.next`, Rust `target*`). `.pytest_cache/` was included and identified as transient. The inventory is a workspace snapshot; it does not claim to include files hidden inside excluded directories.
- Read the text of Markdown, plain-text, TeX, HTML, and reStructuredText files; extracted structural metadata and text from PDFs and Office documents; compared document contents for exact duplicates; and checked relative Markdown links.
- For the large reference library under `documents for competition and very good documentation/books for inspiration in sources/`, checked filenames, PDF metadata, page counts, and text availability in the first three pages rather than reviewing every page. Five PDFs have no usable text layer in the sampled pages and need OCR for a content-level review.
- This is a documentation and organization review, not a code, scientific-method, security, or licensing audit. Document titles and short outlines in the register are for identification, not endorsement.

## Document-collection review

### Competition, business, and reference material

`documents for competition and very good documentation/` contains 98 files (about 433 MB), spanning GEOENERGY submissions/regulations/forms, editable TeX and compiled PDFs, course material, copied software audits, and 40 reference PDFs (about 389 MB). Separate these into clearly named collections such as `competition/`, `references/`, and `project-docs/`, with an index and a source/rights/status field for each item.

Several registration/application documents have duplicate or mojibake filenames, and exact PDF comparison found duplicate copies of a GEOENERGY form and a reference PDF also copied into `public/assets/aistudio/`. Keep one authoritative version of each, preserve a clear source filename, and review personal information before publication. Files whose names indicate LibGen or Z-Library provenance require explicit rights/provenance review before being committed, packaged, or served publicly.

### Product copies, archives, and generated documents

The `oil&gas projects/`, `thepetrolumen/`, `c/`, `petrolumen_tmp/`, and `THE-petrolumen-… (2)/` trees contain further copies, nested repository checkouts, and generated artifacts. Their documentation often repeats older README, audit, environment, and dependency documents. Mark each copy as active, archival, experimental, or temporary; then keep only the chosen active project documentation in the primary navigation.

The `public/assets/aistudio/` area contains exact copies of internal audit/design documents and a PDF duplicate. Anything under `public/` can be delivered to users; remove internal reports and unapproved source material from that delivery path after confirming they are not intentionally published.

### Standalone and personal records

The workspace root also contains GEOENERGY/business-plan attachments, a course-list PDF with a 2026 date, multiple Gaia project presentations/plans, and `late.tex`/`late.pdf`, which are a Portuguese meeting transcript unrelated to application documentation. Store these in a clearly labeled records area with an owner, date, and access/retention policy. The transcript and application forms should not be published with product docs without an explicit privacy review.

### Educational mini-projects

`mini oil and gas projects/` contains 13 small project folders and shared guide/index material. This is a useful, separable educational collection. Add a top-level index with each project's purpose, prerequisites, run/test command, input-data source, and maturity; standardize README headings across the examples.

## Cross-cutting quality checks

- **Exact duplicates:** 42 groups, 115 document instances, and 73 redundant copies. The clearest repeated material is audit/design documentation copied into the competition archive and `public/assets/aistudio/`, plus multiple nested project versions.
- **Broken relative Markdown links:** 30 occurrences were detected across copied/archive/public-asset documentation. No broken relative links were detected in the canonical root guides or `docs/`; fix or stop linking to stale copies rather than treating the archive as authoritative.
- **Empty documents:** 9 zero-byte document-like files were found, including copied environment-state/readme files, a TeX file, and generated text files. Remove or restore these only after confirming they are not intentional placeholders.
- **PDF accessibility:** 5 PDFs had no usable searchable text in the sampled first pages. Mark them as scanned and OCR them if their contents need to be searchable or reviewed.
- **Generated clutter:** TeX build byproducts (`.aux`, `.log`, `.out`, `.toc`, `.fls`, `.fdb_latexmk`, `.synctex.gz`), cache files, build logs, temporary HTML snapshots, and bundle listings are mixed into project trees. Keep generated output out of source documentation and ensure ignore rules cover it.
- **Language and naming:** Core product guidance is English while the main README and several records are Portuguese; both are reasonable, but declare the canonical language and use consistent, descriptive filenames. Normalize mojibake and avoid names such as ` (1)` where a version or status would be clearer.

## Recommended cleanup sequence

1. **Finish history cleanup before publishing.** The current local branch contains earlier commits with large reference PDFs and copied project/build trees. Remove those paths from Git history before any push; a tip-only deletion does not prevent the earlier blobs from being uploaded.
2. **Label the remaining local copies.** The root Vite/React app and `backend/` are now designated active; copied trees are ignored and untracked from Git, but intentionally remain on disk until individually reviewed.
3. **Maintain the documentation index.** The index now distinguishes current, proposed, historical, and archived material. Add owners and last-verified dates as reports are revalidated.
4. **Reconcile audit evidence.** Re-run only the checks needed for present claims, record commit/date/commands/results, resolve test-count conflicts, and link the current report from the root README and `docs/README.md`.
5. **Review privacy and provenance.** Competition/application records and transcript files were moved to a sibling private folder; reference PDFs were moved to a sibling local library. Confirm backups and rights before sharing those folders.
6. **Deduplicate safely.** Exact duplicate public audits were moved to an archive and project copies are untracked but retained locally. Compare remaining nested repositories before deleting any local copies.
7. **Clean generated artifacts.** Ignore rules and `.gitattributes` now cover TeX outputs, caches, Rust/Node build output, and duplicate trees. The generated OpenAPI snapshot is ignored and untracked.
8. **Improve ongoing maintenance.** Add link checking and a documentation freshness checklist to CI or release review; make dates and tested commands mandatory for audits and environment snapshots.

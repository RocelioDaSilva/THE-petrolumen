# Internationalization (i18n) and Localization (l10n) Plan for PetroLúmen

This document outlines a preliminary plan for incorporating internationalization (i18n) and localization (l10n) into the PetroLúmen application. This is a forward-looking plan for future implementation if the application targets a global or multilingual audience.

## 1. Introduction and Potential Benefits

Internationalization is the process of designing an application so that it can be adapted to various languages and regions without engineering changes. Localization is the process of adapting an internationalized application for a specific region or language by adding locale-specific components and translating text.

**Potential Benefits for PetroLúmen:**
*   **Wider User Base:** Makes the application accessible to users who speak different languages.
*   **Improved User Experience:** Users are generally more comfortable using software in their native language.
*   **Competitive Advantage:** Can be a differentiator in the market.
*   **Scalability:** Designing for i18n from the start (or early on) makes it easier to add new languages later.

## 2. Scope
This plan considers i18n/l10n for:
*   **Frontend (PetroLúmen Next.js App):** UI text, date/time formats, number formats, currency formats (if applicable).
*   **Backend (Gaia Genesis FastAPI):** API error messages, potentially email notifications or generated report content if these become multilingual.

## 3. Suggested Approach & Technologies

### 3.1. Frontend (Next.js - `petrolumen/`)

*   **Recommended Library:** `next-intl` or `react-i18next` (with `i18next`).
    *   `next-intl`: Specifically designed for Next.js, offering good integration with App Router and Server Components. Provides typed translations.
    *   `react-i18next`: A popular and powerful i18n framework for React, highly flexible.
*   **Translation File Format:** JSON is common and well-supported. Files would typically be structured by locale (e.g., `locales/en.json`, `locales/es.json`).
*   **Key Management:** Use descriptive keys for translatable strings (e.g., `userMessages.loginFailed` rather than `Login Failed Message`).
*   **Pluralization & Interpolation:** Chosen library should support these features.

### 3.2. Backend (FastAPI - `backend/gaia_genesis/`)

*   **Recommended Library/Approach:**
    *   Python's built-in `gettext` module is the standard for i18n in Python.
    *   For FastAPI, libraries like `fastapi-babel` or `fastapi-i18n` can simplify integration.
    *   Alternatively, custom middleware could handle language negotiation based on `Accept-Language` headers.
*   **Translation File Format:** `.po` and `.mo` files (standard for `gettext`).
*   **Focus:** Primarily for API error messages or any user-facing strings generated by the backend.

## 4. Key Considerations

*   **Locale Detection:**
    *   **Frontend:** Detect user preference from browser settings (`navigator.language`), allow user to select language via UI, store preference (localStorage, user profile).
    *   **Backend:** Use `Accept-Language` header for API requests.
*   **UI/UX Adaptability:**
    *   Text expansion/contraction: Different languages require different amounts of space. UI design must be flexible.
    *   Right-to-Left (RTL) languages (e.g., Arabic, Hebrew) if support is needed.
    *   Date, time, number, and currency formatting (use libraries that support locale-aware formatting, e.g., `Intl` object in JavaScript).
*   **Translation Management:**
    *   Process for translating strings (in-house, third-party service).
    *   Tools for managing translation files (e.g., Weblate, Lokalise, or simple JSON/PO file editors).
*   **Testing:** Include i18n/l10n aspects in testing (e.g., check if strings are translated, UI adapts correctly).
*   **Default Language:** Define a default/fallback language (likely English).

## 5. High-Level Implementation Steps (Future)

1.  **Decision & Prioritization:** Confirm the need and prioritize languages to support initially.
2.  **Library Selection & Setup:**
    *   Choose and integrate i18n libraries for frontend and backend.
    *   Set up directory structures for locale files.
3.  **String Externalization:**
    *   Identify all user-facing strings in the codebase.
    *   Replace hardcoded strings with references to translation keys.
4.  **Translation:**
    *   Create initial translation files for the default language (e.g., English).
    *   Translate content into target languages.
5.  **Locale Switching Mechanism:** Implement UI for users to switch languages (frontend).
6.  **Formatting:** Implement locale-aware formatting for dates, numbers, etc.
7.  **Testing:** Thoroughly test the internationalized application.
8.  **Documentation:** Document the i18n process for developers and translators.

## 6. Conclusion

Implementing i18n/l10n is a significant effort but can greatly enhance the PetroLúmen application's reach and usability. This plan provides a starting point for future consideration. Early planning, even if implementation is deferred, can make the process smoother when the time comes.
